\begin{abstract}
Retrieval-augmented generation (RAG) improves accuracy on repository-level
code completion but spends compute on every instance, including ones where
retrieval is unhelpful or harmful. CARD~\cite{zhang2024card} addresses this
with a learned uncertainty gate that skips retrieval when the model's
zero-shot prediction looks confident. We observe that CARD's uncertainty
signal misses a specific class of failures: \emph{confidently-generated
identifiers that don't actually exist in the repository}. We add a parallel
gate based on static analysis of the model's prediction, which fires
retrieval on instances where any used identifier fails to resolve in the
file's scope, the repository's symbol table, or the language's builtins. The
combined cascade preserves CARD's retrieval savings while
\todo{XX\%} lowering the hallucination rate on CrossCodeEval-Python
(McNemar's $p < $ \todo{XX}), and matching always-retrieve on edit
similarity at \todo{XX\%} of the retrieval cost.
\end{abstract}

\section{Introduction}

Code-completion models trained on large code corpora can reliably continue
short snippets of code, but performance degrades sharply when the right
completion depends on context elsewhere in the same repository --- a
function defined two files away, a class method whose signature lives in a
sibling module, an internal API whose name is conventional only to that
project. Retrieval-augmented generation closes much of this gap by
prepending relevant snippets to the prompt, but it does so indiscriminately,
spending compute on instances where the in-file context already suffices or
where retrieved snippets actively distract the model.

\textbf{Adaptive retrieval} addresses this by deciding, per instance,
whether to retrieve. CARD~\cite{zhang2024card} learns a regressor over
per-token log-probabilities and entropies to predict the zero-shot
output's edit similarity, and triggers retrieval when this prediction is
below a threshold. Our work starts from the observation that CARD's
signal --- aggregated logit confidence --- is blind to a specific failure
mode that is both common and pernicious: hallucinated identifiers.

A model can generate \texttt{self.client.send(\textcolor{red}{msg})} with
high token-level probability across the entire span, even when
\texttt{msg} is not bound anywhere in the surrounding code. CARD will see
high confidence and skip retrieval; the prediction will be silently
wrong; the user will see a plausible-looking line of code that fails at
import time.

\textbf{Contributions.} We add a static-analysis cascade stage to CARD's
decision flow. The new stage runs only when CARD says ``skip'' and triggers
retrieval if the prediction's AST contains an identifier that resolves
nowhere (an \emph{unresolved} reference --- almost certainly a
hallucination) or that resolves in the repository's symbol table but not
the in-file scope (a \emph{cross-file} reference --- retrieval would
demonstrably help). The cascade is asymmetric by construction: static
analysis can only \emph{add} retrievals to CARD's decisions, never remove
them, which bounds the worst-case retrieval count to always-retrieve and
frames the central research question cleanly: \emph{does the extra
retrieval budget reduce hallucinations?}

We evaluate on CrossCodeEval-Python and RepoEval (line and API
subsets), comparing the cascade against vanilla CARD, always-retrieve,
never-retrieve, a static-only ablation, and an oracle upper bound. Our

\section{Method}

\subsection{The cascade}

Given the in-file context $X = (X_{\text{left}}, X_{\text{right}})$ and the
repository $R$, the cascade decides the final prediction $\hat{y}$ in three
asymmetric stages:

\begin{algorithm}[H]
\caption{The cascade pipeline (single-RAG).}
\begin{algorithmic}[1]
\STATE $\hat{y}_0, \text{logits}_0 \gets G(X_{\text{left}}, X_{\text{right}})$
\STATE $\hat{s}_0 \gets \text{Estimator}(\text{features}(\text{logits}_0))$
\IF{$\hat{s}_0 < \TRAG$}
    \STATE $CC \gets \text{BM25}(X_{\text{left}}, R)$
    \STATE \textbf{return} $G(X_{\text{left}}, X_{\text{right}}, CC)$, \textbf{reason}=\texttt{card}
\ENDIF
\STATE $\text{sa} \gets \text{StaticAnalyzer}(\hat{y}_0, X_{\text{left}}, X_{\text{right}}, R)$
\IF{$\text{sa.fires}$}
    \STATE $CC \gets \text{BM25}(X_{\text{left}}, R)$
    \STATE \textbf{return} $G(X_{\text{left}}, X_{\text{right}}, CC)$, \textbf{reason}=\texttt{static\_\{unresolved$|$crossfile\}}
\ENDIF
\STATE \textbf{return} $\hat{y}_0$, \textbf{reason}=\texttt{none}
\end{algorithmic}
\end{algorithm}

\subsection{CARD's uncertainty gate}

We reimplement CARD's single-RAG variant
faithfully~\cite{zhang2024card}: a LightGBM regressor predicts edit
similarity from a 13-dimensional feature vector built from per-token
probabilities and entropies (max, min, mean, std, product, geometric
mean for each, plus generation length). The Estimator is trained on
\todo{50k/250k} (X, y) pairs sampled from The Stack
subset~\cite{kocetkov2022stack}, with the same generator that will run
inference. \todo{Brief note on calibration MSE achieved vs the paper's 0.07.}

\subsection{Static analysis of the prediction}

The novel signal classifies each identifier used in $\hat{y}_0$ as
\textbf{builtin} (Python builtin or visible at the hole), \textbf{in-file}
(in scope at the completion position), \textbf{cross-file} (defined
somewhere in $R$ but not visible in-file), or \textbf{unresolved}
(nowhere). The analyzer uses tree-sitter for fault-tolerant parsing and
tracks scope through imports (including aliased and \texttt{from X import
Y} forms), function parameters, for-loop and comprehension variables,
walrus expressions, \texttt{with} aliases, and lambda parameters.

The stage \emph{fires} if any \textbf{unresolved} or \textbf{cross-file}
identifier is found. When both classes appear in the same prediction we
report the trigger reason as \texttt{static\_unresolved}, as unresolved is
the strictly stronger hallucination signal.

\section{Experiments}

\subsection{Setup}

\paragraph{Datasets.} CrossCodeEval-Python (2{,}665 instances,
\cite{ding2023cce}) is the primary evaluation. RepoEval-line and -api
(1{,}600 instances each, \cite{zhang2023repocoder}) are used to validate
the CARD reimplementation against the paper's published numbers and as a
secondary evaluation surface.

\paragraph{Configurations.} We compare six configurations: (C1)
no-retrieve, (C2) always-retrieve with BM25 top-10, (C3) vanilla CARD,
(C4) our cascade, (C5) static-only ablation (retrieve iff static analysis
fires on the zero-shot output), and (C6) an oracle that runs both C1 and
C2 per instance and keeps whichever has higher edit similarity against the
ground truth.

\paragraph{Metrics.} Following~\cite{ding2023cce} and~\cite{zhang2024card}:
exact match (EM), edit similarity (ES), and identifier-F1 (IdF1) for
accuracy. For efficiency: percent retrieval and mean latency (ms).
For hallucination: \emph{repository-symbol precision} --- the fraction
of identifiers in the prediction that resolve somewhere in scope ---
and a per-instance \emph{hallucination flag} (true iff at least one
unresolved identifier).

\section{Conclusion}

We added a static-analysis cascade stage to CARD's adaptive-retrieval
framework. The new stage targets a specific blind spot of CARD's
uncertainty signal --- confidently-generated identifiers that don't exist
--- and triggers retrieval on instances CARD would otherwise skip. Across
CrossCodeEval-Python and RepoEval, the cascade preserves CARD's retrieval
savings while reducing per-instance hallucination rate by \todo{XX\%}.
